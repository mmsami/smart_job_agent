evaluation automation — what we test and how
=============================================


roadmap (what to do and in what order)
---------------------------------------

P0 — pilot first (before labeling everything)
  pick 1 persona. open only the 6 *_gemma.md files for that persona.
  fill in the "Relevant (0/1)" column only (ignore Quality for now).
  run: python -m src.evaluation.score_results
  confirm it produces output. if anything looks broken, stop and flag it.
  time: ~20 min. goal: catch pipeline issues early, not after 17 hours of work.

P1 — label for P@10 (this is the main labeling task)
  for EACH persona, open only the gemma files — one per method:
    BM25_RAW_gemma.md, BM25_PARSED_gemma.md,
    FAISS_RAW_gemma.md, FAISS_PARSED_gemma.md,
    FAISS_PARSED_NORERANK_gemma.md, FAISS_PARSED_MPNET_gemma.md
  fill in "Relevant (0/1)" only. skip the Quality column entirely for now.
  jobs are identical across all 3 model files for the same method —
  you do NOT need to open the deepseek or claude files for P@10.
  total files: 10 personas × 6 methods × 1 file = 60 files
  split across team: ~20 files each (~3 hrs per person, not 17)
  after labeling: run score_results → H1/H2/H3 done.
  then run: python -m src.evaluation.llm_judge → H4 done automatically (~$0.30).

P2 — quality labels (only if time allows after P1)
  fill "Quality (1-5)" in all 3 model files per method per persona.
  this is the 90-file task. only needed for deeper H4 human comparison.
  not required for a complete report — the llm_judge covers H4.


we have 4 research hypotheses. all scoring is automated except the human relevance
labels in step 2 (which you fill in manually once, then never again).

note on automation: almost everything here runs with a single python command.
the only irreplaceable human task is filling in Relevant (0/1) in the gemma MD files.
that ground truth is what all the automated scoring validates against —
you can't skip it without losing the ability to compare methods against reality.
everything else (P@10, Wilcoxon, bootstrap CI, diversity, preference satisfaction,
LLM judge, Cohen's Kappa) runs fully automatically after labeling is done.


hypotheses
----------

H1: semantic search (FAISS) retrieves more relevant jobs than keyword search (BM25)
    metric: Precision@10 — how many of the top 10 results are actually relevant

H2: parsing the CV into structured fields gives better results than passing raw text
    metric: Precision@10 again, comparing raw vs parsed query for both BM25 and FAISS

H3: LLM reranking improves Precision@10 beyond what retrieval alone gives
    metric: delta P@10 between FAISS_PARSED and FAISS_PARSED_NORERANK, per persona

H4: LLM choice affects explanation quality more than retrieval score
    metric: explanation quality 1-5, scored by Claude as fixed judge across all 3 LLMs


method groups
-------------

each CV is run through 6 retrieval configurations:

  BM25_RAW              — keyword search, raw CV text as query
  BM25_PARSED           — keyword search, structured fields (title + skills) as query
  FAISS_RAW             — semantic search, raw CV text embedded (MiniLM)
  FAISS_PARSED          — semantic search, structured fields embedded (MiniLM)
  FAISS_PARSED_NORERANK — same as FAISS_PARSED but top-10 by similarity only, no LLM reranker
  FAISS_PARSED_MPNET    — semantic search, structured fields embedded (MPNet — stronger model)

then each configuration is run with 3 reasoning models (Gemma, DeepSeek, Claude)
to generate the job match explanations. reranking is always Gemma regardless of
which reasoning model is used — this isolates explanation quality from retrieval.

current matrix: 10 personas x 6 method groups x 3 models = 180 result files
method groups: BM25_RAW, BM25_PARSED, FAISS_RAW, FAISS_PARSED, FAISS_PARSED_NORERANK, FAISS_PARSED_MPNET
(add CVs to data/resumes/ and re-run step 1 — existing results are preserved)


how to run it
-------------

step 1 — generate results
    cd project
    python -m src.evaluation.run_evaluation

    outputs MD and JSON files under evaluation/results/<persona_id>/
    already-complete runs are skipped automatically — safe to re-run after failure
    expect ~10 min for 4 personas (API calls). each re-run is near-instant due to caching.

step 2 — label the MD files (manual, one-time per persona)

    open:  evaluation/results/<persona_id>/<METHOD>_gemma.md
    e.g.:  evaluation/results/cv1/FAISS_PARSED_gemma.md

    each file contains:
      - candidate profile summary at the top (level, skills, industries)
      - a label table with 10 rows — one per job
      - job details section below: description, match reason, missing skills, apply link

    what to fill in:
      column "Relevant (0/1)" — is this job a real match for this candidate?
      column "Quality (1-5)"  — how good is the AI's match explanation?

    relevance rubric (0 or 1):
      1 = correct domain AND within +-1 seniority level
      0 = wrong domain, completely wrong seniority, or clearly irrelevant

    quality rubric (1 to 5):
      1 = wrong or hallucinated (facts that aren't in the job description)
      2 = mostly wrong, vague
      3 = generic but correct — mentions skills that match but no specific evidence
      4 = good — references specific skills/experience from the candidate and job
      5 = excellent — specific, well-reasoned, cites concrete evidence from both sides

    efficiency tip:
      for P@10 (H1, H2, H3) — you only need to fill "Relevant" in the _gemma.md
      per method. jobs are identical across all 3 model MDs for the same method.

      for H4 (explanation quality) — fill "Quality" in all 3 model MDs per method
      (BM25_RAW_gemma.md, BM25_RAW_deepseek.md, BM25_RAW_claude.md) so we can
      compare explanation scores across models.

    labeling assignment (Julia coordinates):
      split 10 personas across 3 teammates — A: 3 personas, B: 3 personas, C: 4 personas
      each teammate labels only their assigned personas (6 gemma files per persona = Relevant only)
      do NOT overlap unless intentional (see inter-rater below)

      workflow:
        1. Julia assigns personas to each teammate in a shared doc or message
        2. each teammate pulls the repo, labels their assigned persona folders, commits, pushes
           git commit -m "label: <persona_id> relevance done"
        3. once all 3 push, Julia pulls everything and runs:
              python -m src.evaluation.score_results   → report.md
              python -m src.evaluation.llm_judge        → llm_judge_report.md
        4. Julia shares report.md with the team — done

      inter-rater reliability (required for H4):
        pick 1 persona. two people label it independently WITHOUT comparing first.
        no code changes needed for either approach below — score_results.py only
        reads files named exactly {METHOD}_{model}.md so any copy is ignored automatically.

        option A — label before committing (simpler):
          both people label their local copy of the shared persona's gemma files
          without pushing. share results via screenshot or message. compare manually.
          agree on final labels, one person commits that version.
          report the agreement rate as a sentence in the paper.

        option B — copy files for rater 2 (cleaner audit trail):
          before anyone labels, copy the shared persona's gemma MDs:
            cp FAISS_PARSED_gemma.md FAISS_PARSED_gemma_rater2.md  (repeat for all 6 methods)
          person A labels the original files. person B labels the _rater2 copies.
          both commit their files. compare side by side after.
          score_results.py ignores the _rater2 files — no impact on scoring.
          better for showing the professor independent evidence.

step 3 — compute scores
    python -m src.evaluation.score_results

    reads labeled MDs, outputs evaluation/results/report.md with:
    - Precision@10 per method per persona + 95% bootstrap CI
    - Wilcoxon signed-rank p-values for H1, H2, H3
    - average explanation quality per model for Experiment B (H4 partial)

step 4 — LLM judge (H4)
    python -m src.evaluation.llm_judge

    Claude Sonnet reads each job result and labels it 0/1, then Cohen's Kappa is
    computed against human labels. Claude is the fixed judge for all 3 LLMs to avoid
    self-preference bias (if Claude judged its own explanations, scores would inflate).
    output: evaluation/results/llm_judge_report.md
    cost: ~$0.60 for full run (10 personas × 6 methods × 10 jobs)


qualitative observations (no extra labeling needed)
---------------------------------------------------

beyond the 4 hypotheses, two lightweight observations add depth to the report.
both are computed automatically from the existing JSON results — no human labels required.

observation A — result diversity
  does the retriever return varied jobs or near-identical ones?
  even if P@10 is high, a system that returns 10 roles from the same company
  or the same seniority band is less useful in practice.
  what we measure (from results JSON, per persona × method):
    - unique companies in top 10
    - unique experience levels in top 10
    - unique job titles (rough dedup by first 3 words) in top 10
  report as: avg unique companies per method, flagging any method that clusters heavily.
  scope: automated, ~1 hr to add to score_results.py. worth doing.

observation B — preference satisfaction
  the professor explicitly asked about this (part-time, employment type).
  does the system return jobs that match the candidate's stated work preferences?
  JobSearchPreferences already has employment_type and work_type fields.
  what we measure (from results JSON):
    - % of top-10 jobs where work_type matches stated preference (where data exists)
  caveat: Kaggle metadata is incomplete for work_type — report coverage alongside the %.
  scope: automated, ~30 min to add to score_results.py. worth doing.

how to frame these in the report:
  label them "qualitative observations" or "beyond precision" — NOT new hypotheses.
  this signals intellectual honesty to the professor without overcommitting to
  statistical tests that require more data or labeling.
  one paragraph each in the results section is enough.


statistical approach
--------------------

primary test: Wilcoxon signed-rank (paired, non-parametric) — right for small N
secondary:    95% bootstrap CI on mean P@10 — illustrative, CIs will be wide at N=10
significance: p < 0.05

note on N: with 10 personas Wilcoxon has reasonable power for directional conclusions.
below 10, results are directional evidence only — not conclusive.

location is excluded from the relevance rubric. BM25 has no location filter by design
so penalising for location would unfairly disadvantage it vs FAISS.

all FAISS methods (RAW, PARSED, NORERANK, MPNET) filter to Kaggle-only results so
H2 compares apples to apples — same job pool, different query construction.


personas
--------

target: 10 CV files in data/resumes/ across 1-2 industries.
filenames (without .pdf) are the persona IDs used throughout the results folder.

to add more personas: drop PDF files into data/resumes/ and re-run step 1.
existing results are preserved — only new personas will be processed.

labeling cost per persona: 6 gemma files × 10 rows = 60 relevance judgments.
  teammate A: labels personas 1-3
  teammate B: labels personas 4-6
  teammate C: labels personas 7-10
Julia runs score_results + llm_judge once all 3 push.


output files
------------

for each persona × method × model you get two files:

  evaluation/results/<persona>/<METHOD>_<model>.json  — machine-readable results + reasoning
  evaluation/results/<persona>/<METHOD>_<model>.md    — human labeling sheet (fill this in)

after labeling + scoring:

  evaluation/results/report.md            — P@10 table + significance tests
  evaluation/results/llm_judge_report.md  — Cohen's Kappa per persona/method


common issues
-------------

"before you start — remove test data first"
    the repo contains test CVs and their result folders used to verify the pipeline.
    delete them before adding real CVs or labeling anything:

        rm -rf project/evaluation/results/cv1
        rm -rf project/evaluation/results/cv2
        rm -rf project/evaluation/results/cv3
        rm -rf project/evaluation/results/Perosona_Finance
        rm -f  project/evaluation/results/report.md
        rm -f  project/evaluation/results/llm_judge_report.md
        rm     project/data/resumes/cv1.pdf
        rm     project/data/resumes/cv2.pdf
        rm     project/data/resumes/cv3.pdf
        rm     project/data/resumes/Perosona_Finance.pdf

    then drop the 10 real CVs into data/resumes/ and run step 1.

"descriptions are empty in the labeling sheet"
    → the job_descriptions_minilm.json file is missing from data/vector_store/
    → download it from Google Drive (same folder as the index)

"run_evaluation crashes on FAISS_RAW"
    → make sure SentenceTransformers is installed: pip install sentence-transformers

"build_vector_store segfaults on Mac (zsh: segmentation fault)"
    → known OpenMP conflict between PyTorch and faiss-cpu on macOS
    → both build scripts already include the fix (TOKENIZERS_PARALLELISM + KMP_DUPLICATE_LIB_OK + numpy normalization)
    → if embedding completed but crash happened after, re-run — vectors_*_cache.npy will skip re-embedding
    → delete vectors_mpnet_cache.npy / vectors_minilm_cache.npy before rebuilding if dataset or chunking changed

"re-run generates nothing (all skipped)"
    → expected behavior — all results already exist
    → to force a specific persona: delete its folder under evaluation/results/

"score_results shows no data"
    → you haven't filled in any labels yet — complete step 2 first
